Beyond Task Completion: Evaluating Agent Planning

Many agents now complete tasks that would have looked impressive a year ago. Completion does not tell us whether an agent planned well. It may have taken a costly detour, called unnecessary tools, or failed to change course when the environment changed.

Reading CostBench sharpened this distinction for me. Task completion asks whether the work was delivered. Planning evaluation asks which path the agent chose, what that path cost, and whether the agent could revise it when the assumptions changed. Those questions matter when a demo becomes a production workflow.

Planning has moved beyond a written plan

PlanBench brought language models back to a classic planning setting: an initial state, a goal, and actions with defined effects. It asks whether a model can form an executable sequence, rather than merely describe a plausible one.

As agents began calling tools and interacting with users, the evaluation problem became more practical. TravelPlanner introduced travel tasks with real constraints. ToolSandbox and τ-bench added stateful tools, multi-turn interaction, and policy adherence. UserBench made incomplete goals and preferences that emerge through conversation part of the test. Planning now includes tool choice, constraint satisfaction, resource trade-offs, clarification, and replanning during execution.

What CostBench adds

CostBench examines whether an agent can complete a task through an efficient tool path and adapt when that path changes. Its travel-planning environment has six scenario types and four stages: identify preferences, search, filter, and select. Atomic tools perform individual steps; composite tools bundle them. Several valid paths can reach the same goal, but they carry different costs. Costs are reassigned across samples, so memorizing a fixed route does not solve the benchmark.

The environment also introduces four kinds of disruption: a tool is disabled, a user preference changes, a tool's cost changes, or a composite tool disappears. Some changes are announced; others must be inferred. This makes the test closer to an operating system that must keep making decisions than to a single puzzle with a fixed answer.

Three results that changed my view

First, completion and efficient planning separate sharply. In the paper's static five-step setting, Claude Sonnet 4 reached 93.58% task completion but 59.84% exact match to the optimal tool path. GPT-4o reached 90.29% completion and 13.65% exact path match. A high final success rate can hide wasteful execution.

Second, longer tasks expose weak path coherence. When the task sequence grew from five steps to eight, even GPT-5 fell below 75% exact path match in the reported setting, while weaker models fell much further. Short workflows are a poor proxy for long business processes.

Third, change is harder than following a plan. Tool bans and cost changes were especially damaging. Cost changes are subtle because the agent must notice that its original route is no longer economical. Under the most difficult cost-change condition, the paper reports GPT-5 at 34.91% exact path match. Many systems can execute a plan; fewer can reconsider one mid-flight.

Where planning evaluation fits

The field has progressed through several useful stages: symbolic action-and-state tests such as PlanBench; realistic constrained tasks such as TravelPlanner; multi-turn, stateful environments such as τ-bench and ToolSandbox; and newer work on dynamic constraints, resource scheduling, and cost-aware replanning. Flex-TravelPlanner and R-ConstraintBench probe harder constraint changes. WildToolBench draws attention to messy real user behavior, including implied intent and switches between tasks and conversation.

Planning is one layer of agent quality. Basic capabilities include understanding instructions, filling tool arguments, and retaining context. Planning chooses and orders actions under constraints. User-facing outcomes then ask whether the task was completed safely and acceptably. Evaluating only the top layer makes it hard to explain a failure in the middle.

For researchers, a planning benchmark can isolate whether the agent failed to enumerate routes, compare costs, or notice a changed condition. CostBench's coverage-rate analysis suggests that agents often fail before optimization: they never consider enough candidate paths. For product teams, unnecessary steps add latency and cost even when the final answer is right. For business leaders, that difference determines whether a workflow is economical at scale.

A practical evaluation stack

  1. Outcome: task completion, correctness, and user satisfaction.
  2. Process: tool sequence, unnecessary calls, and path quality.
  3. Adaptation: response to changed constraints, failed tools, and revised user goals.
  4. Economics: tokens, API and tool costs, latency, compute, and human intervention.

The next planning tests should use more realistic user behavior and production costs, including latency and random failures. They should also feed training: a benchmark can become an environment in which agents learn to notice and repair poor plans. A production evaluation system needs to see the agent's decisions, not just its final answer.
